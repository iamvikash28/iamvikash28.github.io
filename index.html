CASE STUDY 01 · REQUIREMENTS + OPERATIONS ANALYTICS

E-commerce Order Management System (OMS)

Investigating delivery delays, payment failures, stock mismatches, cancellations, refunds, and support demand—and defining the requirements and measures for a better order-management process.

BRDAs-Is / To-BeSQLPower BIUser storiesUAT / RTM

Business problem and context

A hypothetical e-commerce business faces fragmented order handling and limited visibility into fulfilment, payments, inventory, refunds, and customer support. The project frames an OMS improvement initiative and identifies where operational friction appears.

Objective and key questions

  • Where do late deliveries and dispatch delays cluster?
  • Which payment methods fail most often?
  • Where do checkout sessions drop off?
  • Which categories show higher returns or inventory mismatches?
  • What requirements and KPIs would help teams monitor improvements?

Data and tools

Ten synthetic CSV tables covering orders, items, payments, shipments, returns, support tickets, inventory audits, customers, products, and funnel events. SQLite SQL analysis, Power BI dashboard specification/report, Excel tracker, Word BRD, process diagrams, and UAT/traceability artifacts.

Approach and methodology

  • Mapped current and proposed order workflows.
  • Documented stakeholders, scope, assumptions, risks, 17 functional and 10 non-functional requirements.
  • Created 17 user stories with acceptance criteria, a prioritized backlog, and a four-sprint plan.
  • Queried operational KPIs and designed a four-page Power BI view.
  • Prepared 25 UAT cases and a requirements traceability matrix; 21 pass and 4 fail in the illustrative test run.

Key findings from the synthetic dataset

24.8%Delivered orders arrived after the promised date (5,296 delivered orders; 1,315 delayed).
11.3%Net Banking payment-attempt failure rate, versus 4.7% for UPI.
16.7%Fashion return rate, the highest category rate in the analysis.
55.2%Support tickets categorized as delayed-order issues; order-status inquiries add another 21.2%.
₹9.5 lakhValue associated with 137 pending refunds in the synthetic data.
18.4%Of product-view sessions ended in an order in the analyzed funnel.

Business recommendations

  • Review dispatch handoffs and compare carrier/warehouse performance against a consistent SLA definition.
  • Investigate Net Banking failures by reason and assess clearer recovery/retry messaging.
  • Analyze Fashion return reasons and product-level patterns before changing assortment or product information.
  • Prioritize delay-related support drivers and expose order status proactively.
  • Monitor pending-refund age/value and inventory discrepancies through exception-focused KPIs.

Expected business value and evidence

The intended value is better prioritization, more transparent operational monitoring, and testable system requirements. No post-implementation impact was measured. The project includes a BRD, SQL schema/queries/results, process diagrams, tracker, dashboard assets/specification, UAT cases, and RTM.

CASE STUDY 02 · SERVICE OPERATIONS + SLA ANALYTICS

IT Service Desk Transformation & SLA Analytics

A service-desk workflow and analytics project to make ticket demand, resolution, SLA risk, backlog ageing, and category suggestions easier to review.

Business case / BRDMySQL 8SQL analyticsFlask prototypePower BI guideClassifier POC

Business problem and context

IT support teams need consistent visibility into incoming tickets, open backlog, ageing, SLA compliance, resolution times, reopened tickets, and team workload. Manual triage can also create inconsistent categorization. This project simulates a small service desk using synthetic tickets.

Objective and key questions

  • How much ticket demand and unresolved backlog exists?
  • How do resolution times vary by category?
  • Which resolved tickets met the defined SLA, and which open tickets are overdue?
  • Where is backlog ageing concentrated?
  • Can ticket text suggest a category to assist—not replace—human triage?

Data and tools

MySQL 8 schema and analytical queries, synthetic ticket generation (5,000-ticket setup), Python, Flask prototype, TF-IDF + Logistic Regression classifier, test suite, and Power BI build guide.

Approach and methodology

  • Defined illustrative priority-based calendar-hour SLAs: Critical 4h, High 8h, Medium 24h, Low 72h.
  • Designed SQL checks for ticket volume, average/median resolution time, SLA compliance, open overdue tickets, ageing, reopen rate, workload, and data quality.
  • Built a prototype to review tickets, create tickets, update status, and preview category suggestions.
  • Evaluated a text classifier on a held-out synthetic test split and documented the limitation.

What the project demonstrates

7 categoriesTicket classes covered by the text-classification proof of concept.
SQL KPI setVolume, resolution, SLA, backlog ageing, reopen rate, workload, and data-quality checks.
Human reviewCategory suggestions are advisory; staff should validate before assignment.

Business recommendations

  • Use a shared SLA definition and report resolved-ticket compliance separately from open overdue tickets.
  • Review ageing and priority together to identify escalation candidates.
  • Use category and team workload views to guide triage and capacity discussions.
  • Keep a human-in-the-loop review for suggested categories and monitor errors by class.
  • Validate KPI definitions and classifier performance with real, appropriately governed data before adoption.

Expected business value and evidence

The prototype and queries could support more consistent triage and operational reviews, but no real-world time saving or SLA improvement has been measured. Deliverables include SQL schema/analytics, application code, data-quality checks, classifier evaluation, documentation, and tests.

ANALYTICS PROJECT 01 · SALES PERFORMANCE + CUSTOMER ANALYTICS

Jewellery Sales Analysis — FY 2024

Analyzing a jewellery retailer’s 2024 sales across gold, silver, and diamond products to understand category contribution, product performance, customer mix, payment methods, and city-level revenue.

ExcelPower BISales KPIsProduct analysisCustomer segmentation

Business problem and context

A jewellery business needs a consolidated view of sales performance across product categories, 22 products, customer types, payment methods, and 10 cities. The report is designed to help stakeholders identify revenue concentration and areas for further commercial investigation.

Objective and key questions

  • Which jewellery categories and products contribute most revenue?
  • How does revenue vary by month and city?
  • What is the mix of new, returning, and premium customers?
  • Which payment methods are most frequently used?
  • Where should managers investigate assortment and local sales opportunities?

Data and tools

650 synthetic sales transactions dated in FY 2024, covering category, product, metal purity, quantity, unit price, revenue, customer type, city, and payment method. Analysis workbook in Excel and a multi-page Power BI report.

Analytical approach

  • Summarized revenue and order count, and calculated average transaction value.
  • Compared revenue by category, month, product, customer type, payment method, and city.
  • Designed report pages for overall performance, product contribution, and customer/city patterns.
  • Used rankings and category shares to identify where follow-up analysis may have the greatest value.

Key findings from the dataset

₹3.66 croreTotal recorded revenue across 650 synthetic transactions.
₹56,367Average revenue per transaction (total revenue divided by 650 rows).
58.5%Revenue contribution from Diamond products.
₹39.5 lakhRevenue from the top product, Diamond Pendant.
₹48.1 lakhHighest city revenue in this dataset: Chennai.
36.2%Returning customers as a share of transaction rows; this is not a unique-customer retention rate.

Business recommendations

  • Review Diamond assortment, stock availability, and margin data before increasing investment, because revenue contribution alone does not establish profitability.
  • Use monthly and city-level views to identify seasonal patterns and locations worth deeper investigation.
  • Compare returning-customer behaviour using customer-level measures such as repeat purchase frequency and time between orders.
  • Combine revenue with gross margin, inventory turnover, and discount data in a future version to support better commercial decisions.

Expected value and project files

The dashboard can help stakeholders scan sales mix and identify follow-up questions; no sales uplift or profit impact was measured. Supporting files include the dashboard PDF and Excel analysis workbook.

ANALYTICS PROJECT 02 · RETAIL SALES + PROFITABILITY ANALYTICS

Retail Store Analytics — 2023–2024

Analyzing 5,000 synthetic retail order records to compare revenue, profit, product/category mix, regional performance, customer segments, and discount levels.

SQLPower BIExcelProfitability KPIsRegional analysis

Business problem and context

Retail managers need to distinguish high-revenue products from profitable ones and understand how sales vary across categories, regions, periods, and customer segments. Discounting also needs to be considered alongside margin rather than revenue alone.

Objective and key questions

  • What are the overall revenue, profit, margin, and average order value?
  • Which categories and products contribute the most sales?
  • Which regions generate the greatest revenue?
  • How do reported margins vary across discount bands?
  • What should be monitored to avoid trading revenue growth for weaker profitability?

Data and tools

5,000 synthetic order rows from 2023–2024 with sales, cost, profit, margin, discount, product/category, region/state, and customer segment. SQL analysis scripts, Excel workbook, and an interactive Power BI-style dashboard/report.

Analytical approach

  • Calculated aggregate revenue, profit, weighted profit margin, and average transaction value.
  • Compared product/category revenue and profit, region performance, and monthly trends.
  • Grouped transactions into discount bands and compared revenue and average row-level margin.
  • Designed dashboard filters for year, region, category, segment, and quarter to support self-service exploration.

Key findings from the dataset

₹64.98 lakhTotal revenue across 5,000 synthetic order rows.
₹26.85 lakhTotal recorded profit; aggregate profit divided by sales is about 41.3%.
54.5%Electronics share of total revenue, the largest category contribution.
₹1,300Average sales value per row, rounded.
₹13.67 lakhSouth region revenue, the highest regional total in this dataset.
56.96% → 40.79%Average row-level profit margin across the no-discount and 21%+ discount bands, respectively.

Business recommendations

  • Track both revenue and profit when reviewing top products and categories.
  • Review high-discount transactions and low-margin products before changing promotion policy.
  • Compare regional results with category mix and order volume before reallocating inventory or marketing spend.
  • Add time-series comparisons and validate seasonality before drawing conclusions from monthly changes.

Expected value and project files

The report provides a consistent starting point for sales and profitability reviews; no real-world commercial impact was measured. Supporting files include the dashboard PDF, SQL analysis, and dashboard HTML prototype.

ANALYTICS PROJECT 03 · CUSTOMER ANALYTICS + MACHINE LEARNING

Customer Segmentation & RFM Analysis

Combining customer, order, and website-engagement data to profile purchasing behaviour, segment customers, and identify groups for targeted retention and marketing strategies.

PythonPandasRFM AnalysisK-MeansPower BIData Quality

Business problem and context

Businesses need to understand which customers purchase frequently, generate higher revenue, are newly active, or may be at risk of becoming inactive. This project turns transaction and engagement data into interpretable customer profiles that support retention and marketing decisions.

Objective and key questions

  • Which customers are high-value, loyal, or newly active?
  • Which customers appear at risk of becoming inactive?
  • How do customer count and revenue share differ by segment?
  • How do recency, frequency, and spending vary across segments?
  • Which segments warrant targeted retention or re-engagement efforts?

Data and tools

Customer CRM, orders, and web-log datasets combined at customer level. Processed with Python and Pandas, with Excel analysis outputs and a Power BI dashboard/report.

Analytical approach

  • Standardized column names, parsed dates, removed duplicate customer/order IDs, handled missing values, and excluded invalid order amounts.
  • Built customer-level order and engagement summaries.
  • Calculated Recency, Frequency, and Monetary (RFM) metrics plus average order value and purchase-velocity features.
  • Scaled behavioural features and used K-Means clustering, with elbow and silhouette analysis to assess cluster counts.
  • Profiled segments by customer count, revenue share, recency, frequency, and spending.

Key highlights from the project

3 datasetsCRM, orders, and web logs combined into one customer-level view.
RFMRecency, Frequency, and Monetary metrics, plus average order value and purchase velocity.
K-MeansClustering on scaled features, with elbow and silhouette analysis to assess cluster counts.
4 profile measuresSegments compared by customer count, revenue share, recency, and spending.
Data qualityDuplicates removed, dates parsed, missing values handled, and invalid order amounts excluded.
Power BISegment results presented in a dashboard/report for stakeholder review.

Business recommendations

  • Prioritize retention initiatives for high-value and loyal customer groups.
  • Investigate at-risk or dormant customers for targeted re-engagement.
  • Compare customer share with revenue share by segment before allocating marketing effort.
  • Use segment profiles to shape marketing hypotheses and measure future campaign outcomes.

Expected value and project files

The segmentation gives stakeholders interpretable customer groups to guide follow-up decisions; no campaign uplift or revenue impact was measured. Supporting files include the Python analysis, Excel outputs, and Power BI dashboard.

ANALYTICS PROJECT 04 · GENERATIVE AI + SQL

Natural Language to SQL Chatbot

A conversational analytics prototype that translates plain-English questions into read-only SQL queries, executes them against a sample SQLite shop database, and displays results in a Streamlit interface.

PythonGemini APIPrompt EngineeringSQLiteSQL SafetyStreamlit

Business problem and context

Non-technical users often need data answers but lack the SQL skills to write queries independently. The prototype explores a natural-language interface for asking questions about sales, customers, products, and orders.

Objective and key questions

  • Can plain-English questions be translated into accurate SQL?
  • How can the model be grounded in the actual database schema?
  • How can generated queries be restricted to safe, read-only operations?
  • How can SQL and results be shown clearly to non-technical users?

Data and tools

Python, Streamlit, Pandas, Google Gemini API, SQLite, and a sample relational database with customers, products, and orders.

Analytical approach

  • Read the SQLite database schema and supplied table/column context to the language model.
  • Used the Gemini API to generate one SQL query from the user's question.
  • Removed response formatting and validated the generated query before execution.
  • Allowed only safe, read-only SELECT queries and blocked unsafe or multi-statement SQL.
  • Ran approved queries and presented the SQL and results in a Streamlit chat UI.

Key highlights from the project

3 tablesCustomers, products, and orders in the sample SQLite database.
1 queryA single SQL statement generated per question using the Gemini API.
SELECT-onlyUnsafe and multi-statement SQL is blocked before execution.
Schema-groundedTable and column context is supplied to the model with each question.
TransparentThe generated SQL is shown alongside the results.
StreamlitChat-style interface built for non-technical users.

Business recommendations

  • Review generated SQL for correctness before relying on results in decisions.
  • Apply database-level access controls in addition to SELECT-only validation before any real-data use.
  • Test with a broader set of business questions to measure query accuracy.
  • Extend to larger schemas with logging and user feedback in a future version.

Example questions: Which product category sells the most? Show the top customers by revenue. What are total sales by city? How many orders were placed in a selected year?

Expected value and project files

Designed to reduce the technical barrier to exploratory querying; no measured productivity improvement or production deployment is claimed. AI-generated SQL must be checked for correctness and access controls before use. SELECT-only validation is a safety measure, not a guarantee that every query is accurate or production-ready.
